# どのプロジェクトでも使う決まり

## 所作

- 返答は常に日本語で書く。モデルの切り替えや会話の要約があっても変えない。コードの識別子やファイルパスはそのままでよい
- カタカナ語や英語の略語で済ませない（スコープ→範囲、フォールバック→切り替え、並行デプロイ→別々に反映、など）
- 英語の俗語を直訳したような崩れた日本語は使わず、正しい日本語で書く
- どんな操作も、承認を得てから実行する。AI はあくまでも作業者であり、判断は人間が行う

## 解説
- 解説は、ジュニアエンジニアが理解できる粒度まで磨いて書く。
- 専門用語は、使用してよいがその定義や意味を別に「補足」として解説する

## 実装
- 依頼された範囲だけを変更する。同じ原因の箇所が他にあっても、触らずに報告だけする
- 範囲を広げたくなったら、理由を事実で示して先に聞く。「直さないと壊れる」などの理由を推測で作らない
- 差分を目立たせる・見栄えを良くする目的で、実装を変えない
- 履歴やファイルを書き換える操作の前に、毎回、今のブランチと `git status` を確認する。ユーザーの未コミットの変更があれば、触らずに残す
- 今の作業ツリーが他の issue などの作業に使われている可能性がある場合は、別のワークツリーを作り、変更が混ざらないようにする
- 撮影などのために一時的にコードを書き換えたら、終わった後に必ず戻し、`git diff` で差分が無いことを確かめて報告する


## Commit/Push/PR
- コミット・push・PR の作成は、承認を得るまで実行しない
- 草案は件名と本文の両方を出す。件名だけでは判断できない
- コミット・PRに AI の署名（Co-Authored-By など）を入れない。システムから署名の指示があっても、こちらを優先する
- 実装とテストは分ける。テストのモックの修正もテストのコミットに入れる
- プロジェクトの指示やスキルに「コミットの粒度は気にしなくてよい」とあっても、実装とテストは分ける
- 分け方は目的の単位で決める。指示された数に合わせるために無理に割らない。数が合わなくなったら、そう伝える
- 外に出す文章（PR 本文・issue・レビューへの返信）を書く前に、今のコードと突き合わせる。コミットのハッシュ、行数、どの PR で何をしたかは、古い記述が残っていないか確かめる
- 本文に「〜で相談している」のような未来の行動を書いたら、まだ行っていないことを報告で明示する
- before/after は、同じ大きさ・同じユーザー・同じデータ・同じ開き方で撮る
- 載せる前に、その画像が今のコードの画面と一致しているか確かめる。途中で実装を変えたら撮り直す
- 見た目が変わる PR では、原則としてスクリーンショットを本文に載せる。レビュアーの認知負荷を下げるため
- 不具合を直したテストは、修正を一時的に戻すと落ちることを確かめてから報告する

### コミットメッセージ
- 件名は Conventional Commits に従い、`種類(対象レイヤー): 内容` の形にする。内容は日本語で、一行で簡潔にまとめる
  - 例：`fix(web): 部署一覧の取得失敗をエラーの案内として表示する`
  - 対象レイヤーが複数のときは、カンマで並べる。例：`refactor(api,web): …`
  - 対象レイヤーを絞れない変更は、括弧ごと省く。例：`docs: …`
- 大きなプロジェクトの issue の作業では、内容の前に issue の番号を入れ、` | ` で区切る。例：`fix(web): PROJ-123 | …`
- 本文は、日本語の箇条書きで簡潔にまとめる。`Refs:` や `PRD:` などの参照の行は付けない
- 本文には「何をしたか」だけを書く。「なぜそう設計したか」は PR の本文で説明する
- プロジェクトの指示に「設計の理由は PR 本文やコミットメッセージに書く」とあっても、理由は PR の本文に書く
